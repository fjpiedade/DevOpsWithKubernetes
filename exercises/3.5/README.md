# Exercise 3.5 – The Project, Step 14: Kustomize on Google Kubernetes Engine

## Objective

Configure the Todo application project to use Kustomize and deploy it to Google Kubernetes Engine (GKE).

This exercise builds on the application developed in Exercise 2.10. The application manifests are organized and managed through a single Kustomize configuration.

The main objectives are:

- Configure Kustomize to manage all application Kubernetes resources.
- Adapt persistent storage configuration for GKE.
- Deploy the application to a Google Kubernetes Engine cluster.
- Expose the application externally using a GKE Ingress.
- Verify that the application and its supporting services are operational.

## Application Architecture

The application is deployed in the Kubernetes namespace `project` and includes:

- **Todo frontend** – provides the user interface.
- **Todo backend** – exposes the REST API and processes Todo requests.
- **PostgreSQL StatefulSet** – stores Todo records persistently.
- **Todo generator CronJob** – periodically creates Todo entries.
- **Kubernetes Services** – provide internal communication between application components.
- **ConfigMaps and Secret** – provide application configuration and database credentials.
- **PersistentVolumeClaims** – provide persistent storage.
- **Ingress** – exposes the Todo application externally.

All application source code, Dockerfiles and Kubernetes manifests are maintained in this exercise directory.

## Kustomize Configuration

The project uses a root-level `kustomization.yaml` file to define the Kubernetes resources required by the application.

The configuration includes:

- Namespace definition.
- PersistentVolumeClaim for frontend image storage.
- Application ConfigMaps.
- PostgreSQL Secret and StatefulSet.
- Todo frontend Deployment and Service.
- Todo backend Deployment and Service.
- Todo generator CronJob.
- GKE Ingress.

The resources are managed together through Kustomize instead of applying individual manifest files manually.

### Kustomize structure

The relevant project structure is:

```text
exercises/3.5/
├── kustomization.yaml
├── namespace.yaml
├── manifests/
│   ├── configmap.yaml
│   ├── ingress.yaml
│   ├── postgres.yaml
│   ├── todo-app-deployment.yaml
│   ├── todo-app-service.yaml
│   ├── todo-backend-deployment.yaml
│   ├── todo-backend-service.yaml
│   └── todo-generator-cronjob.yaml
├── persistent-volume/
│   └── persistentvolumeclaim.yaml
├── todo-app/

```

### Render the Kustomize configuration

From the repository root, inspect the resources generated by Kustomize:

```bash
kubectl kustomize exercises/3.5/
```

This renders the complete Kubernetes configuration without applying it to the cluster.

## Google Kubernetes Engine Configuration

The application is deployed to a GKE cluster.

The deployment uses GKE-compatible Kubernetes resources and storage configuration.

### Persistent storage

The original local Kubernetes storage configuration was replaced with dynamically provisioned GKE PersistentVolumeClaims.

The StorageClass used by the application is:

```yaml
storageClassName: standard-rwo
```

This StorageClass uses the GKE Persistent Disk CSI provisioner.

Both the frontend image cache and PostgreSQL use persistent storage.

### Ingress

The application is exposed through a GKE Ingress using the `gce` Ingress class.

The Ingress routes both `/` and `/todos` to the `todo-app-svc` Service.

The configuration uses:

```yaml
spec:
  ingressClassName: gce
```

The GKE Ingress controller provisions the external HTTP Load Balancer and its associated resources.

## Deployment

### Prerequisites

- A Google Cloud project with billing enabled.
- A running Google Kubernetes Engine cluster.
- `gcloud` CLI installed and authenticated.
- `kubectl` configured to access the GKE cluster.
- Kustomize support through `kubectl`.
- The application container images available in the configured container registry.

### Verify the cluster context

```bash
kubectl config current-context
```

Verify that the expected GKE cluster is selected before applying the resources.

### Deploy the application

From the repository root, apply the complete project using Kustomize:

```bash
kubectl apply -k exercises/3.5/
```

Kubernetes creates or updates all resources defined in the root `kustomization.yaml`.

### Verify the deployment

Check Deployments, StatefulSets, Pods and Services:

```bash
kubectl get deployments,statefulsets,pods,services -n project
```

Check ConfigMaps, Secrets, PersistentVolumeClaims and Ingress:

```bash
kubectl get configmaps,secrets,pvc,ingress -n project
```

Check the storage claims:

```bash
kubectl get pvc -n project
```

The PersistentVolumeClaims should reach the `Bound` state.

Check the Ingress:

```bash
kubectl get ingress -n project
```

The GKE Ingress controller provisions an external IP address. Provisioning and health-check synchronization may take several minutes.

## Application Validation

### Verify the application Pods

```bash
kubectl get pods -n project
```

The frontend, backend and PostgreSQL Pods should reach the `Running` state.

The Todo generator CronJob creates Jobs according to its configured schedule. Completed generator Pods are expected.

### Verify the Ingress backend health

The Ingress creates Google Cloud Load Balancer backend services.

The backend health can be inspected using:

```bash
gcloud compute backend-services list --global
```

For the Todo application backend, use the corresponding backend service name:

```bash
gcloud compute backend-services get-health BACKEND_SERVICE_NAME --global
```

The application backend should report `HEALTHY`.

### Access the application

Retrieve the external Ingress IP:

```bash
kubectl get ingress todo-app-ingress -n project
```

Open the application in a browser:

```text
http://INGRESS_EXTERNAL_IP
```

### Test the application endpoints

Test the frontend:

```bash
curl -i http://INGRESS_EXTERNAL_IP/
```

Expected result: HTTP `200 OK` with the Todo application HTML.

Test the Todo API through the frontend:

```bash
curl -i http://INGRESS_EXTERNAL_IP/todos
```

Expected result: HTTP `200 OK` with a JSON response containing the Todo entries.

Create a Todo using the application interface in the browser and verify that it appears in the Todo list.

## Result

Exercise 3.5 successfully configures the Todo application project with Kustomize and deploys it to Google Kubernetes Engine.

The application resources are managed through a single `kustomization.yaml` configuration.

The deployment uses GKE-compatible persistent storage and a GKE Ingress to expose the application externally.

The frontend, backend and PostgreSQL components were deployed successfully, and the application was verified through the external Load Balancer.

The Todo application was accessible through a browser, and Todo creation and retrieval through the application API were confirmed.

## Cleanup

GKE resources and external Load Balancer resources may incur Google Cloud charges.

After completing the exercise and saving the required repository changes, remove the application resources:

```bash
kubectl delete -k exercises/3.5/
```

After the Ingress and its associated Load Balancer resources have been released, delete the GKE cluster if it is no longer required.

Verify that no unused Load Balancer resources or persistent disks remain in the Google Cloud project.
